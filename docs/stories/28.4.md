## Dev Notes
- **NodeLoader Usage Pattern**: Use `NodeLoader.load(node_id)` which returns a `NodeConfig` object containing the `task` field with `name`, `description`, and `role_supplement` attributes
- **No Dual-Read Mechanism**: Do NOT implement fallback to `execution_context.get("task_name")` - per Epic requirements, no dual-read mechanism should be used
- **Import Considerations**: `NodeLoader` is typically located in `autoBMAD/nodes/loader.py`
- **NodeConfig Structure**: After EPIC-26, NodeConfig v2 provides `task` field with:
  - `task.name` → maps to old `task_name`
  - `task.description` → maps to old `task_description`
  - `task.role_supplement` → maps to old `role_supplement`
- **Log Impact**: Changing from `task_name` to `node_name` in logs is intentional - node_name is always available in execution_context and provides sufficient traceability
- **Testing Strategy**: Tests that previously verified task field propagation through execution_context should now verify direct NodeLoader calls via mocking

### Completion Notes
Story 28.4 migration is complete. All consumer code has been updated to read task information directly from NodeConfig via NodeLoader instead of from NodeExecutionContext. This maintains the Single Source of Truth principle and eliminates the dual-read mechanism as required by the Epic.

Key architectural decisions:
1. **No fallback mechanism** - Per Epic requirements, no dual-read to `execution_context.get("task_name")` was implemented
2. **NodeLoader as single source** - All task fields (name, description, role_supplement) are now read directly from `NodeConfig.task`
3. **Minimal context contract** - NodeExecutionContext remains a 9-field contract with only runtime-dynamic fields
