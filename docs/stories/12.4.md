## Story
**As a** developer,
**I want to** implement the `close` method in CheckpointManager,
**So that** I can properly release resources and prevent connection leaks when pipelines complete or need cleanup.

## Acceptance Criteria
- [ ] `close(pipeline_id)` closes only the checkpointer for the specified pipeline_id
- [ ] `close()` (without arguments) closes all cached checkpointers
- [ ] After closing a checkpointer, calling `get_or_create` with the same pipeline_id creates a new instance
- [ ] Logging is implemented for both single and bulk close operations
- [ ] The cache is properly cleared after close operations
- [ ] Multiple calls to close with the same pipeline_id do not raise errors

## Tasks / Subtasks
- [ ] Task 1: Implement `close(pipeline_id: str)` method for closing a specific pipeline's checkpointer
- [ ] Task 2: Implement `close()` method (no arguments) for closing all cached checkpointers
- [ ] Task 3: Add structlog logging for close operations with appropriate log levels
- [ ] Task 4: Ensure cache dictionary is properly cleared after close
- [ ] Task 5: Handle edge case: calling close on non-existent pipeline_id should not raise error
- [ ] Task 6: Verify idempotency - multiple close calls should not cause issues

## Dev Notes
- The `close` method should be called by HybridOrchestrator when a pipeline completes or is cancelled
- Consider adding integration with pipeline lifecycle hooks for automatic cleanup
- The method should be async to match the async nature of CheckpointManager
- Logging should use structured logging with pipeline_id context
- The `close` method does NOT need to call `aclose()` on the AsyncSqliteSaver itself - the cache removal is sufficient as the saver will be garbage collected when no references remain
- Consider adding metrics/observability for tracking close operations in production
