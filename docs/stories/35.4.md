## Story
**As a** system architect,
**I want** to add version control to the UpdateContextTool,
**So that** concurrent updates to shared_context can be tracked and potential conflicts can be detected in retry scenarios.

## Acceptance Criteria
- [x] Each update increments `_metadata.version` (monotonically increasing integer)
- [x] `_metadata.updated_at` is set to current ISO timestamp (UTC) on every update
- [x] Version info is returned in ToolResult with `timestamp` and `version` fields
- [x] Backward compatible - existing `shared_context` without `_metadata` works correctly (auto-initializes metadata)
- [x] Version format follows pattern `v{version}_{timestamp_ms}` (e.g., `v1_1712404245123`)

## Dev Notes
- **File Location**: `autoBMAD/docuswarm/tools/update_context.py`
- **Current State**: The tool writes directly to SQLite without version tracking
- **Version Format**: Use `v{version}_{timestamp_ms}` where:
  - `version` is an integer starting at 1, incrementing on each update
  - `timestamp_ms` is milliseconds since epoch for collision resistance
- **Metadata Structure**:
  ```python
  _metadata: {
      "version": int,        # starts at 1, increments on each update
      "updated_at": str      # ISO 8601 UTC timestamp
  }
  ```
- **Backward Compatibility**: Handle missing `_metadata` gracefully:
  - Auto-initialize with version=0 and updated_at=null
  - First update sets version to 1
- **Timestamp Format**: Use ISO 8601 with timezone (e.g., `2026-04-06T10:30:45Z`)
- **Concurrency Note**: This story adds version tracking but NOT optimistic locking yet. Locking will be handled in a future story if needed.
