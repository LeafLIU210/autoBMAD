## Dev Notes

### Database Schema
```sql
CREATE TABLE shared_context_history (
    id INTEGER PRIMARY KEY AUTOINCREMENT,
    pipeline_id TEXT NOT NULL,
    node_id TEXT NOT NULL,
    operation TEXT NOT NULL,  -- 'set', 'append', 'remove'
    key TEXT NOT NULL,        -- dot-notation key path
    old_value TEXT,           -- JSON serialized (NULL for new keys)
    new_value TEXT,           -- JSON serialized (NULL for removals)
    timestamp TEXT NOT NULL,  -- ISO 8601 format
    version TEXT,             -- version string from _metadata.version
    FOREIGN KEY (pipeline_id) REFERENCES pipeline_state(pipeline_id)
);

-- Indexes for common queries
CREATE INDEX idx_history_pipeline ON shared_context_history(pipeline_id);
CREATE INDEX idx_history_timestamp ON shared_context_history(timestamp DESC);
CREATE INDEX idx_history_node ON shared_context_history(node_id);
CREATE INDEX idx_history_key ON shared_context_history(key);
```

### Implementation Approach
1. **Transaction Safety**: History recording must be in the same transaction as the context update to ensure consistency
2. **JSON Serialization**: Store old_value and new_value as JSON text for flexibility
3. **Version Tracking**: Include the version number from `_metadata.version` (set in Story 35.4)
4. **Performance**: Use indexes on commonly queried fields; consider pagination for large histories

### Integration Points
- **Story 35.4 (Version Control)**: History table should store the version number incremented by UpdateContextTool
- **Story 35.1 (DB Refresh)**: History records help debug issues with context refresh in executor.py
- **StateManager**: Extend `autoBMAD/docuswarm/storage/state_manager.py`

### Error Handling Strategy
- History recording failures should be logged but not prevent the main update
- Use try-except around history recording to isolate failures
- Consider adding a `history_recorded` flag to update results for debugging
